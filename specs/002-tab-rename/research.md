# Research: 标签右键重命名

## 1. 入口放在哪

**Decision**: 在现有标签右键菜单 `tabMenu` 中，仅当 `isRealFilePath(path)` 时加入「重命名…」，调用已有 `promptRename(path)`。草稿（`draft://`）、对比（`compare://`）、尾随台（`tail://`）不加入。键盘菜单键 / Shift+F10 已调用同一 `tabMenu`，不另做快捷键。

**Rationale**: 标签右键、菜单键已经是同一函数。文件树右键已经用 `promptRename` 完成「预填文件名、拒绝斜杠、同名 EXISTS、失败提示」。标签侧缺的是入口，不是另一套改名对话框。

**Alternatives considered**:

- 标签上双击就地改名：规格假设明确沿用文件树的输入框，不新做行内编辑。
- 给标签单独做一套改名：会和文件树的名称规则、失败文案分叉，违反 FR-011。

## 2. 磁盘改名是否新写后端

**Decision**: 继续使用现有 IPC `file_rename`（`fileRename`）。它拒绝设备路径、源不存在报 NotFound、目标已存在报 EXISTS、不覆盖，并用 `std::fs::rename`。

**Rationale**: 标签改名与文件树改名是同一文件系统操作。新建命令没有新语义，还会拆出第二份错误哨兵。

**Alternatives considered**:

- 先复制再删除：非原子，失败会留下两份或丢原文件，违反数据保护。
- 允许覆盖：规格 FR-003 明确禁止。

## 3. 单文件标签如何迁移，且不误迁子路径

**Decision**: 标签入口只改一个文件名。成功后按精确路径迁移该标签，不得使用现有 `TabStore.renamePath` 的「路径前缀 + 分隔符」目录语义。目录改名仍走文件树，继续用前缀迁移。

**Rationale**: `renamePath('E:\\old', 'E:\\new')` 会改写 `E:\\old\\a.txt`。若用户把文件 `E:\\notes` 改成 `E:\\notes-old`，同一规则会误改已打开的 `E:\\notes\\a.txt`。规格要求同目录其他文件、子目录中已打开文件不受影响。

**Alternatives considered**:

- 直接复用 `store.renamePath`：对无扩展名文件会把同名目录下的标签一起改掉。
- 关闭再按新路径打开：会丢未保存修改、滚动和标签身份，违反 FR-004。

## 4. 活动编辑视图的路径

**Decision**: 活动视图若是 `EditView` 或 `LivePreviewView` 且其路径就是该文件，继续用现有 `relocate(newPath, () => fileRename(...))`，让改名排进该视图的保存队列，成功后才更新视图路径。其他视图（文本流式、图片、CSV、PDF、Office 预览）在 `fileRename` 成功后再迁移标签与元数据，不先销毁视图。

**Rationale**: `relocate` 已保证保存与改名不交错，避免改名后保存写回旧路径。非编辑视图没有这条队列；先销毁再重开会造成空白帧，也会丢掉预览位置。改名成功后更新视图自身持有的路径；若该视图类型无法原位更新路径，再销毁当前挂载并按新路径重挂，缓冲与脏标记已迁到新路径。

**Alternatives considered**:

- 所有类型都先 `destroyView()`：活动图片/预览会闪一下，且未保存文本若尚在视图对象里有丢内容风险。
- 改名后强制重新 `openFile`：会把未保存缓冲换成磁盘内容。

## 5. 扩展名变化后的展示

**Decision**: 磁盘改名成功后，用现有快速种类识别（只看新扩展名，不读文件内容）更新该标签的 `route` 与 `language`。用户锁定过的路由（`routeLocked`）不覆盖。识别变化时，作废该路径的暂存视图并按新路由重挂；识别不变则保持当前视图，只改路径。

**Rationale**: 规格要求只改扩展名后按新扩展名展示，且不另存一份。完整内容嗅探会把大文件读进打开路径，违背分块读取约束；扩展名已能决定图片 / PDF / Word / 表格 / 文本语言。无扩展名或未知扩展名保持文本路由，与现有打开规则一致。

**Alternatives considered**:

- 不更新路由：`.png` 改成 `.md` 仍当图片，违反规格。
- 改名后走完整 `openFile`：多一次磁盘探测，且会重置滚动、可能覆盖用户锁定的视图。

## 6. 关联状态迁移清单

**Decision**: 精确路径迁移时一并搬迁：

- 标签身份：顺序、激活、滚动、书签、草稿字段（真实文件通常为空）、路由锁
- 文档会话：`documents.rename`（脏标记、编码、大小、修改时间、只读、删除标记、缓冲、恢复快照）
- 壳层记忆：`modeMap`、`wrapMap`、`csvDelimiters`、`hlOverride`、`wysiwygHeadings`、`switchAnchor`、`tabLock`、`mruOrder`、`closedTabs` 中等于旧路径的项
- 暂存视图：路径等于旧路径的停车记录改为新路径；路由未变则保留，路由变了则销毁
- 恢复：把挂起快照写到新路径，并丢弃旧路径快照（现有 `recoveryDiscard`）
- 打开备忘：旧路径 `textOpenMemoInvalidate`；若语言属于 Office/PDF，旧路径 `ooxmlClose`，新路径下次打开再取

不迁移：其他标签、子路径、目录树里未打开的兄弟文件。

**Rationale**: 这些 Map 都以路径为键。漏迁会出现「标签已是新名，脏点/只读锁/编码仍挂在旧路径」或保存写回旧文件。

**Alternatives considered**:

- 只改 `TabStore`：壳层 Map 继续指向旧路径，状态栏和保存会错。
- 改名后整页重建会话：丢失未保存内容和标签顺序。

## 7. 最近打开与收藏

**Decision**: 新增一个只改路径记录的持久化操作，在同一持久化锁内读—改—写 `recent.json` 与 `favorites.json`。只替换规范化后与旧路径完全相等的条目（含收藏组内条目）。新路径若已在列表中，保留新路径那条、去掉旧路径那条，不制造重复。不按目录前缀改写。改名成功后前端调用它并 `refreshRecents()`。持久化失败只警告，不回滚已经成功的磁盘改名，也不回滚标签迁移。

**Rationale**: 现有 `recent_add` 会把路径插到队首并截断，不能表达「原位改名」。`favorites_toggle` 会取消收藏。规格要求记录指向新路径且未涉及记录不变。配置 JSON 只增操作、不改字段，符合向后兼容。

**Alternatives considered**:

- 前端 `recent_remove` 再 `recent_add`：顺序变成最近，且两次写之间可能丢更新。
- 在 `file_rename` 里顺手改 JSON：命令层应保持薄，且文件改名不应因配置写失败而报改名失败。

## 8. 只读、大小写、文件已删除

**Decision**:

- 标签锁和全局只读不禁用重命名菜单。磁盘只读或占用由 `file_rename` 失败体现，用现有失败文案。
- 仅大小写不同的新名称照常发给 `file_rename`。Windows 上 `std::fs::rename` 对同一文件的大小写变更可成功；若某平台返回 EXISTS，再提示同名已存在，不另写平台分支。
- 源文件不存在返回 NotFound。前端把该哨兵显示为文件已不在，不创建新文件。现有错误串若只落到通用「重命名失败」，实现时补一条「文件已不在」文案，不改变哨兵字符串。

**Rationale**: 规格把只读限制在正文。大小写与占用是文件系统结果，不应在前端先猜。不新建空文件是现有 `file_rename` 已保证的。

**Alternatives considered**:

- 只读标签隐藏重命名：与规格边缘情况相反。
- 前端先 `stat` 再改名：多一次往返，仍无法消除占用竞态。

## 9. 并发与失败顺序

**Decision**: 先完成磁盘 `file_rename`，成功后才迁移内存与配置记录。对话框确认到 IPC 返回期间，用户可以切换别的标签；迁移按路径查找，不按打开菜单时的下标。若该标签已被关闭，磁盘改名仍然保留，内存不再迁一个不存在的标签，最近/收藏仍更新。若目标在确认后被其他操作占用，IPC 失败，内存不动。

**Rationale**: 先改内存会在磁盘失败后留下指向不存在路径的标签。按下标迁移会在对话框打开时关错标签，项目里关闭守卫已经为此改成按路径。

**Alternatives considered**:

- 改名前锁定整个标签栏：超出本次范围，也妨碍用户继续看其他文件。
