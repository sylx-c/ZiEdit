# 图片查看器补强 — 设计（短文档）

状态：已定稿并实现（ac-010，2026-10-29）；实现与审查记录见 image-view-enhance-plan.md 与 .superpowers 工作区账本。
范围：仅图片查看器（PDF/pdf.js 为后续独立项目，另立文档）。

## 意图与为什么

图片查看是 PRD 核心能力之一。现状（`src/image-view/view.ts`，156 行）：
缩放/适应/100% 已存在且接线完整，但用户实测**没发现入口**（可发现性差）；
放大后只能靠滚动条移动（无拖拽平移）；无旋转；超大图无保护（整幅解码可致
WebView 卡死/OOM，对比文本侧 10MB、PDF 侧 100MiB 上限，图片侧无上限）；
交互行为零测试覆盖。

## 目标

1. **可发现性**：信息条重构为常显缩放控件「[−] [百分比] [+] [适应窗]」，
   双击图片循环 适应窗→100%→适应窗。
2. **拖拽平移**：按住拖动（左键/中键）平移，复用容器原生滚动
   （程序化 scrollLeft/Top，保留滚动条与滚轮语义），grab/grabbing 光标。
3. **旋转**：90° 步进（信息条或工具栏 ⟲⟳ 按钮），旋转后适应窗按交换后的
   宽高重算；SVG/GIF 同样适用（CSS transform 层面）。
4. **大图守护**：解码前探测尺寸，超阈值不直接解码，展示卡片：
   原始尺寸 + 「用系统查看器打开」（复用 open_with_default）+「仍要加载」。
5. **测试**：新增前端行为测试（vitest+jsdom）+ Rust 侧探测单测。

## 非目标 / 反目标

- 不做任意角度旋转（90° 步进足够）；不做批注、裁剪、滤镜、GIF 帧控制、ICC。
- 不做降采样缩略图管线（见「方案」B，留作后续按需升级）。
- 不引入 panzoom/viewer 类前端库；不重写 canvas 渲染（SVG 必须走 `<img>`）。

## 约束

- 无新前端依赖；信息条/工具栏遵循 H-2 上下文段模式。
- 常规路径图片字节仍走 asset 协议不经 IPC（性能红线）；守护探测是一次性
  小 IPC（仅读文件头），不违反红线精神。
- i18n zh/en 同步；tests/ 按验收编号组织（顺延现有最大编号）。

## 方案（大图守护的实现取舍）

- **A. 零成本守门（推荐）**：Rust 新命令 `image_probe` 只解析文件头取
  {width, height, format}（建议引 `imagesize` crate：单一用途、无传递膨胀、
  覆盖 png/jpeg/webp/bmp/gif；备选手写 ~120 行四格式头解析，符合本项目
  手写 PDF tokenizer 的文化，但正确性风险自担）。阈值：任一边 > 16384px
  （Chromium 纹理上限，超过渲染必坏）或像素 > 66MP（≈264MB RGBA）→ 守护卡片。
  优点：零解码成本解决卡死风险；缺点：超大图不能在应用内看。
- **B. 降采样预览**：加 `image` crate 生成缩略图经临时文件展示，标注
  「预览（降采样）」。优点：应用内可看；缺点：新重依赖（编译+包体
  ~1.5MB）、大图解码耗内存/时间只是从 WebView 挪到 Rust。
- 选 A，理由：真实风险是「打开即卡死」，A 以最小代价消除；B 在确有
  应用内查看超大图的需求时再升级，届时 A 的探测与卡片直接复用。

## 已定决策（对话拍板 / 我的裁量）

- 整体路线：渐进增强现有 `<img>` 实现，不重写、不引库（用户已选）。
- 平移实现：程序化滚动而非 transform translate（保留原生滚动条语义）。
- 双击循环：适应窗→100%→适应窗（不进入自由倍率态）。
- 旋转入口：信息条按钮（工具栏上下文段已有 4 钮，再加 2 个旋转钮会挤，
  旋转放信息条；如走查发现信息条过挤再移工具栏）。
- 阈值常量 16384/66MP 写成具名常量便于调整。
- `imagesize` crate 作为探测实现（用户可否决改手写）。
